نظام تسجيل الجودة — Test Checklist (server-backed)
==================================================

Run these first; they cover most of it without a browser:

    cd server
    npm run check-env
    npm run data-check
    npm start                      (leave running)
    node scripts/test-security.js  (in a second terminal)

All three should end with no problems. Then work through the screens.


0. SETUP
   - Delete server/data/iso-quality.db, then `npm run seed -- --demo`.
     The database should be recreated with 5 departments, 8 services,
     7 users, 1 holiday and 9 requests.
   - Start the server twice in a row. The second start must not duplicate
     anything (the seed is idempotent; the schema migration is too).

1. SIGN-IN
   - Each of the four test accounts signs in and lands on the right scope.
   - A wrong password is refused with the same message as an unknown user —
     it must not reveal whether the account exists.
   - A deactivated account cannot sign in.
   - Reload the page while signed in: the session survives, no re-login.
   - Sign out, then press Back. The old page must not still work.
   - With LDAP_URL set, a real AD account signs in with either its username
     or its email, and appears in إدارة النظام as an Active Directory account.

2. NORMAL USER (hisham)
   - Sees only his own requests, in the table AND in the dashboard cards.
   - The employee filter offers only himself.
   - Opening another person's رقم الطلب directly is refused.
   - Can file a request; only his own department's active services are offered.
   - Can close his own request; cannot close anyone else's.
   - Excel exports exactly the filtered rows.

3. SUPERVISOR
   - Sees his whole department and nothing outside it.
   - Employee filter is limited to his department's staff.
   - Can still only close his OWN requests (Phase 1 rule).
   - إدارة النظام and سجل التدقيق are not reachable, by menu or by URL.

4. POWER USER
   - Sees the whole organisation; department and employee filters are
     organisation-wide and dependent on each other.
   - Department performance table appears.
   - Is NOT مدير النظام: no إدارة النظام.

5. DEADLINES  (the part worth testing carefully)
   - File a 3-working-day request today. The deadline must skip Friday,
     Saturday and any public holiday in between.
   - Now declare a public holiday landing ON that deadline. The message must
     report how many deadlines were recalculated, and the request's deadline
     must move.
   - Delete that holiday. The deadline must come back to where it was.
   - Closed requests must NOT move in either direction.
   - Change a machine's clock and reload: the dates must not change. They are
     computed on the server.
   - A request whose deadline passed over a weekend shows as متأخر with
     0 أيام التأخير. That is correct — late on the calendar, no working days
     lost yet.

6. CLOSING
   - Closing on or before the deadline: no delay panel, الإنجاز في الوقت = نعم.
   - Closing after it: the delay panel appears and the reason is required.
   - Choosing "أسباب أخرى" requires the text; saving without it is refused.
   - A closing date before the request date, or in the future, is refused.
   - Closing an already-closed request is refused.

7. إدارة النظام
   - Users: add, edit, activate/deactivate, reset password.
     · Deactivating someone must end their open sessions — have them signed in
       on another browser and confirm they are thrown out on their next click.
     · A reset password forces a change at next sign-in, and blocks every other
       screen until it is done.
     · مدير النظام cannot change his own role or deactivate himself.
   - Departments: unique prefix enforced; the prefix cannot be edited after
     creation; deactivate rather than delete.
   - Services: the code is generated from the department prefix (MNT-003…);
     duplicate names inside one department are refused; a changed duration
     applies to NEW requests only.
   - Holidays: end date = start + duration in CALENDAR days.
   - Audit log: read-only, newest first, and shows readable Arabic
     "before → after" — not raw JSON.

8. AUDIT TRAIL
   - Every one of the following leaves an entry: sign-in, sign-out, failed
     sign-in, new request, closed request, and each إدارة النظام change.
   - Edit a user's department and role. The entry must name only the fields
     that changed.
   - There is no way to edit or delete an entry from anywhere in the app.

9. SECURITY  (scripts/test-security.js covers these; re-check by hand if the
   authorisation code is touched)
   - A token with someone else's id is served as its own account, not theirs.
   - A token with no jti is refused.
   - Role or admin claimed inside the token is ignored.
   - A token signed with the wrong secret is refused.
   - Demote someone while they are signed in: it applies on their next click,
     not in eight hours.

10. RESET
   - `npm run seed -- --reset --demo` returns everything to the starting state.
   - The old in-app "إعادة البيانات التجريبية" button now explains that the
     data is on the server and does not delete anything.
