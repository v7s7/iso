Deploying نظام تسجيل الجودة to the server
==========================================

Repo:  https://github.com/v7s7/iso.git
Port:  4100   (docTracking has 3300 — they do not clash)

Run these on the SERVER machine, in Git Bash or PowerShell.


1. CLONE
--------
    cd <wherever docTracking lives>
    git clone https://github.com/v7s7/iso.git
    cd iso/server


2. INSTALL
----------
    npm install

This is the step most likely to fail, and it is worth knowing why before it
happens. better-sqlite3 is a native module: it needs a compiled .node binary
for the exact Node version in use. npm tries to download a prebuilt one and,
failing that, to compile it — which needs Python and Visual Studio build
tools. On the laptop this was written on, neither was available.

If it fails with "gyp ERR! find Python", docTracking on this same server
already has a working copy of the identical version. Use it:

    npm install --ignore-scripts
    mkdir -p node_modules/better-sqlite3/build/Release
    cp <path-to-docTracking>/server/node_modules/better-sqlite3/build/Release/better_sqlite3.node \
       node_modules/better-sqlite3/build/Release/

Then check it actually loaded:

    node -e "new (require('better-sqlite3'))(':memory:'); console.log('ok')"

This only works while both projects run the SAME Node version. Check with
`node -v` — it was built for Node 20 (ABI 115). If the server runs a different
major version, the copy will not load and the module has to be built properly.


3. CONFIGURE
------------
    cp .env.example .env

Then edit .env and set these four:

    JWT_SECRET      generate it, do not invent one:
                      node -e "console.log(require('crypto').randomBytes(64).toString('hex'))"
                    Use a DIFFERENT secret from docTracking's. They are separate
                    systems; sharing a signing key means a token minted by one
                    is valid in the other.

    PORT=4100

    CLIENT_URL=http://10.27.17.20:4100
                    The address people actually type. Only used when the page is
                    served from a different origin than the API — which it is
                    not here — but keep it correct anyway.

    LDAP_URL=ldap://10.27.16.5
                    Already in .env.example. Leave the rest of the LDAP block
                    as it is; it matches docTracking.

Optional, for the "استيراد من Active Directory" screen only:

    LDAP_BIND_DN=<a read-only account, e.g. svc.iso@swd.bh>
    LDAP_BIND_PASSWORD=<its password>

Sign-in against AD works WITHOUT these. Only browsing the directory needs them.

Now check the whole file:

    npm run check-env

It says what is wrong and how to fix it. Do not continue until it says Ready.


4. CREATE THE DATABASE
----------------------
    npm run seed -- --demo

Creates server/data/iso-quality.db with the 5 departments, 8 services, the
test accounts and 9 sample requests.

For a real go-live with no sample data and no test accounts, edit the USERS
array in scripts/seed.js first, then run `npm run seed` with no --demo.

The database is NOT in git and never will be — it is this server's own data.


5. REACHING IT FROM OTHER MACHINES
----------------------------------
Do NOT change the firewall to find out whether you need to. Test first — there
is a good chance nothing needs doing at all.

Start the server (step 6), then from another machine open:

    http://10.27.17.20:4100

If it loads, the port is already reachable and there is nothing to do here.
That is the likely outcome: docTracking already serves port 3300 from this same
machine, so node.exe has been allowed through before, and a Windows rule created
for a program covers whatever port it listens on.

If it does NOT load, stop and raise it with whoever administers this machine.
An inbound firewall rule on a government server is their decision and their
change record — not a line to paste from a deployment note. Tell them:

    program:   node.exe  (the same one docTracking already runs)
    direction: inbound
    protocol:  TCP
    port:      4100
    scope:     the internal network only — this must not be reachable from
               outside, it has no TLS

Until then the site still works fully when opened ON the server itself, at
http://localhost:4100 — enough to finish the setup and test everything.


6. START
--------
    npm start

Leave the window open. Closing it, signing out, or rebooting stops the site —
the same arrangement docTracking uses, so it is a known quantity here.

Surviving a reboot means running it as a Windows service, and on this machine
that is a change to raise with whoever administers it rather than something to
set up from a deployment note: PM2's `pm2 startup` installs a service and needs
Administrator, and a service that starts before anyone logs in is exactly the
kind of thing a server owner wants to have approved.

If and when they agree, the shape of it is:

    npm install -g pm2
    pm2 start index.js --name iso
    pm2 save
    pm2 startup        # prints a command that must be run as Administrator

Until then, the open window is fine — and it has one honest advantage: the site
stops when nobody is meant to be using it.


7. CHECK IT
-----------
From the server:        http://localhost:4100
From another machine:   http://10.27.17.20:4100

Sign in as admin@test.local / Test123.

Then, with the server still running:

    npm run data-check
    npm run test-flow
    npm run test-security

All three should end clean.

  data-check      read-only; safe any time, including on live data.
  test-security   forges tokens against the running server and asserts they are
                  refused. Run it after any change to the auth code.
  test-flow       walks a real user's path end to end. It WRITES — it keeps one
                  account (flow.check@test.local, left deactivated) and files
                  one request per run. Run it now, while the database is still
                  demo data; do not run it once real records are in there.


UPDATING LATER
--------------
    cd iso
    git pull
    cd server
    npm install          (only if package.json changed)
    npm start

.env and data/ are gitignored, so a pull never touches the server's own
configuration or its records. Schema changes apply themselves on the next
start — db/index.js migrates the file in place.

Back up before a pull that changes the schema. Do NOT copy the .db file while
the server is running: recent writes live in the -wal file beside it and a
plain copy will miss them. Use:

    sqlite3 data/iso-quality.db ".backup data/backup-YYYY-MM-DD.db"


BEFORE REAL USERS
-----------------
  [ ] Delete or disable the four test accounts (hisham, supervisor, power,
      admin @test.local). They have a published password.
  [ ] Set SUPER_ADMIN_USERS in .env to a real person — it is the lockout
      failsafe, and no screen in the app can remove it.
  [ ] Map the AD groups in server/config/directory-map.json. Run
      `npm run ad-probe` to see which groups actually exist and how many people
      are in each; it prints them in the exact spelling the file expects.
  [ ] Confirm at least one real account reaches إدارة النظام.
  [ ] Decide whether the site should survive a reboot (see PM2 above).
